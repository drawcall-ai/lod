# Find the cost of a slow LOD view

Replay short moving windows at the slow positions. Match camera path, instance placements, wind time, physical render size, MSAA and shadow refreshes. For LOD-only measurements, exclude unrelated draws such as terrain, sky and final presentation, retaining the lights, scheduled shadow passes and instance selection that the Lods use. Check the change again in the complete scene, where foreground occlusion can differ.

Compare a fresh-page traversal with a warmed repeat. Record whether derived assets were already cached so a cold bake can be distinguished from first use of a cached level. Record median and p95 CPU render submission separately from GPU timestamps for the camera, each active shadow cascade and selection compute. CPU and GPU overlap. For GPU busy time, take the union of timed intervals. A 120 Hz frame has 8.33 ms for the entire experience. Per-pass readbacks belong in a diagnostic replay since waiting for the GPU changes frame pacing. An uninterrupted flight measures how frames actually arrive.

| Observation | Control and interpretation |
| --- | --- |
| High CPU submission with few visible objects | Compare submitted draws with the actual instance counts in the GPU indirect commands for that pass. The CPU uses conservative bounds. Three can prepare materials and bindings and encode a draw before the GPU consumes a count of zero. Tighten cluster bounds when too many levels qualify. Merge compatible parts when many live draws always switch together. Tiny separate Lods add submissions of their own. |
| High GPU time with few draws | Count triangles **times live instances**, separately for camera and shadows. Restrict the suspect pass to a one-pixel scissor while keeping geometry and submissions. Substantial residual time points toward vertex processing, primitive setup or fixed pass costs. Try an earlier switch to the next representation and inspect the image at the boundary. |
| Cost falls sharply under the scissor | Omit one suspect level or material in one pass and time again. Removing an occluder can slow the surviving draws. If opaque foreground geometry hides expensive cut-outs, compare drawing the opaque geometry first within the same render order. Explicit group or object orders can prevent that saving. To test shading, keep ordering, depth, discard and alpha coverage while replacing only final RGB with a constant. Compare impostor depth and parallax independently. Quad area, alpha-covered samples and samples passing depth answer different questions. None directly measures shader invocations or memory bandwidth. |
| Suspected bandwidth bottleneck | A matched-image comparison that changes texture storage or vertex stride while preserving geometry and shading tests sensitivity to memory access. Cache locality and decoding can change too. Attributing stalls specifically to DRAM needs device counters. |
| First approach hitches, repeat is smooth | Count source generation, texture uploads, CPU node-graph builds and GPU pipeline creation separately. Three can reuse a pipeline after building multiple material graphs. Reuse material objects where textures, uniforms, update hooks and lifetime can be shared. Equal constructor parameters or identical shader text alone cannot establish that. Precompiling moves first-use work earlier. Sharing compatible resources at their owner can eliminate it. |

For a proposed group or cluster LOD, compare the same replacement geometry selected once by the parent and selected independently per child. Hold placement, shading and switch sizes comparable, then count how many children actually choose different detail. This isolates the gain from independent selection from the gain of drawing cheaper geometry. Repeat the baseline after the candidate and compare motion at the switch before adopting a small timing difference.
